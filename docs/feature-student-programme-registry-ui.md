# Student and Programme Registry UI

## Functional flows

Staff can open `/dashboard/students` or `/dashboard/programmes`, search active records, filter by lifecycle status, choose a supported sort field and order, page through results, and inspect a safe detail projection. Registrars and administrators can create and edit records. Administrators can archive or withdraw records through the API-backed Archive action.

Student registration supports full name, normalized email, date of birth, and programme selection. The registration dialog labels the field `Programme`, loads active programme names, uses `programmeId` as the form field name, and submits the selected programme ID as its value. Student ID, academic year, and enrollment reference are generated by the registration API. Programme forms support name, fee, discount, coupon, coupon usage limit, and status. Terminal statuses remain visible but cannot be reactivated by the API.

## Validation and permissions

Client validation mirrors the API boundaries for required strings, email, dates, academic years, non-negative monetary values, and allowed statuses. The API remains authoritative; conflict, missing programme, invalid transition, unauthorized, forbidden, and server errors are mapped to accessible alerts. Read access is staff-and-above, write controls are registrar-and-above, and archive controls are admin-only.

## States and accessibility

The registry exposes loading skeletons, empty results, paginated results, inline detail, form validation, disabled submit controls while saving, and role-aware action visibility. Search and filters have labels, validation uses `aria-invalid` and alert text, status badges are supplementary to text, and detail headings/actions are keyboard reachable.

## API boundary

All requests use `AxiosInstance` from `lib/axios-client.ts` with credentials enabled. List payloads are read from `response.data.data` and `response.data.pagination`; detail and mutation payloads are read from `response.data.data`. Programme monetary strings are converted to numbers only at form submission. No password, OTP, session, or other secret is stored in client state.

## Assumptions and handoff

The existing server session supplies the role to each page shell. The Students registry loads active programmes through the existing `/api/programmes` list endpoint before the registration dialog is used. Each dropdown option displays the programme name and submits its numeric ID through `programmeId`; the API remains authoritative for programme availability. The API migration must be applied and PostgreSQL reachable before these pages can load real records. The repository Jest configuration uses the Node environment and does not include component roots, so no browser tests were added; API tests remain the focused automated coverage and the UI is ready for integration-level browser coverage later.
